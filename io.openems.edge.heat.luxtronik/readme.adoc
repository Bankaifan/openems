= Alpha Innotec / Novelan Luxtronik SHI

OpenEMS Edge driver for the Luxtronik Smart Home Interface (SHI) over Modbus TCP.
The driver supports read-only monitoring by default and *explicitly enabled*
remote control using the documented SHI holding registers.

== OpenEMS integration model

This is a standard OpenEMS Edge device component, not an independent heat-pump
scheduler or dashboard application. It registers the factory
`Heat.Luxtronik.SHI` and implements the existing `Heat` and
`ElectricityMeter` interfaces. As with other OpenEMS Modbus devices, the
readable measurements and writable controls are exposed as component channels.

The Luxtronik SHI supports mode-dependent setpoints, offsets, blocks and
power *limits*. It does **not** expose a continuously adjustable requested
heating-element power as supported by the OpenEMS `ManagedHeatElement`
interface for my-PV/ASKOMA electric heaters. Therefore this driver must not
claim to implement `ManagedHeatElement` or automatically accept an OpenEMS
`TARGET_ACTIVE_POWER` signal: the semantics are different.

Similarly, OpenEMS `Controller.Io.HeatPump.SgReady` controls physical
SG-Ready relay outputs. It is not a generic Modbus-heat-pump controller and
cannot be wired to SHI registers without a separately defined, correctly
validated mapping. The manufacturer cautions against simultaneous SHI and
SG-Ready control.

The standard OpenEMS configuration/component browser can display these
channels. The graphical Heat widgets and App Manager entries are
factory-specific and do not appear solely because a new `Heat` component
is installed. Further energy scheduling, if required, should use existing
OpenEMS abstractions and explicit device-specific capability mapping,
without reimplementing the wider energy-management platform.

== Prerequisites

* Enable SHI in the Luxtronik controller (Modbus TCP port 502, default unit 1).
* Do *not* operate the separate Smart Grid (SG Ready) logic alongside SHI
  controls. The manufacturer warns that the two control mechanisms interfere.
* Ensure your controller firmware is compatible with SHI (v3.90.1 or newer).
  Some extended functions may require firmware 3.92 or installation-specific
  options; verify them before enabling `enableExtendedRegisters`.
* Restrict access to Modbus TCP to a trusted network (no public port forwarding).
* Prefer a single write-control owner (OpenEMS vs. other smart-home software).

== Standard App Manager installation

The OpenEMS App Manager now provides `App.Heat.Luxtronik` in the existing
Heat category. It creates a `Heat.Luxtronik.SHI` component and a standard
`Bridge.Modbus.Tcp` component (port 502) from the user's IP address.
Monitor-only operation is the default; SHI write access and optional
extended registers are explicit installable properties.

As with other OpenEMS heat apps, users can also configure the device and
Modbus bridge manually in the standard component editor. The app does not
create a proprietary controller or add a custom UI dashboard.

== Configuration

Component factory: `Heat.Luxtronik.SHI`.

[cols="1,1,3"]
|===
|Property |Default |Effect

|`modbus_id` |`modbusLuxtronik0` |Modbus TCP bridge of the SHI
|`modbusUnitId` |`1` |Modbus TCP unit ID
|`readOnly` |`true` |No Modbus FC6 write tasks are created. Switch to
`false` only after confirming SHI activation and firmware compatibility
|`enableExtendedRegisters` |`false` |Opt in to optional level, overall
heating and circulation registers (only if supported by firmware and wiring)
|===

All SHI holding-register channels use the `ShiWriteRegister` enum. The names
in the OpenEMS UI use this enum's names, e.g.
`heatLuxtronik0/HEATING_OFFSET` and `heatLuxtronik0/POWER_LIMIT_TENTHS_KW`.

== Supported control families

* Heating: mode, return-temperature setpoint, temperature offset, level, block
* DHW: mode, desired temperature, offset, level, block, extra DHW demand
* Mixing circuits 1 through 3: individual heating and cooling setpoints,
  modes and offsets, optional heating levels
* Cooling and pool blocking, room target (when RBE is configured)
* Heat pump electrical power limitation: no limit, soft PV limit, hard limit
* Overall heating offset/level and circulation trigger where firmware supports

Mode values for heating/DHW/mixing circuits: `0` no influence,
`1` absolute setpoint, `2` offset and `3` increased/decreased level.
Each setpoint or offset requires its corresponding mode to be set and
*read back from SHI first*. Requests are rejected if the mode is not yet
effective or the relevant SHI capability is unavailable.

The power limitation uses `POWER_LIMIT_MODE=0` (no limitation),
`1` (soft PV-aware limitation), or `2` (hard/§14a limitation).
`POWER_LIMIT_TENTHS_KW` is an integer in 0.1-kW steps, range 0..300.
For example, 40 represents 4.0 kW. Set mode to 1 or 2 and wait for
read-back before writing the power limit. The driver **does not** itself
implement the grid operator's §14a request interpretation, legal compliance
verification, or price optimization; it exposes the appropriate SHI channels
for a higher-level OpenEMS controller to drive.

Temperature setpoints and offsets use 0.1-degree increments, as documented
by ait-deutschland. Negative offsets are transmitted as signed INT16.
All outgoing values are range-checked and *rejected*, never silently clipped.
DHW absolute setpoints are additionally constrained by the system's reported
minimum/maximum temperatures.

== Read-only channels

Input registers provide current heating state, return/flow/outside
temperatures, DHW temperature, error code, current heating capacity
and electrical power. The standard OpenEMS `Heat` channels for current
and target temperature and the `ElectricityMeter` active power channel
are mapped. When writes are enabled, the driver reads back supported SHI
holding-register values (Modbus FC3) and capability flags (FC2).

== Safety and timeout

* The default is monitor-only; no FC6 task exists until control is explicitly
  enabled. Changing `readOnly` should recreate the component.
* Invalid values, unavailable SHI options and mismatched control modes are
  rejected before generating a write.
* The manufacturer specifies an SHI watchdog: after approximately 15 minutes
  without a master's requests, externally applied settings revert to defaults.
  This is implemented in SHI, not in OpenEMS.
* Do not depend on SHI power limitation as the sole implementation of legally
  required §14a grid control without integration and verification of the
  external signal and the actual heat-pump response.
* Test in a Modbus simulator before enabling writes on a real heat pump.
  Nothing in the driver modifies equipment merely because it is activated.
